# コード実装

対象: 実装コードとテストを書く作業。

## テスト先行

- **テストを先に書く**: 実装者は、失敗するテストを 1 本書いて赤を確認してから実装に入る ／ 例: `npm test -- auth` が 1 件 fail する状態を作る ／ 失効: なし
- **1 サイクル 1 振る舞い**: 実装者は、赤 → 緑 → 整理 の 1 サイクルで 1 つの振る舞いだけを扱う ／ 例: 「無効トークンで 401 を返す」で 1 サイクル ／ 失効: なし
- **バグ修正は再現テストから**: 実装者は、バグ修正の最初の commit で再現テストを追加する ／ 例: issue の入力値をそのままテストケースにする ／ 失効: なし
- **テストは実挙動を検証する**: 実装者は、モックの呼び出し回数ではなく戻り値・状態・副作用を assert する ／ 例: HTTP status と body を assert する ／ 失効: なし
- **緑にするために本番コードを直す**: 実装者は、テストが赤のとき実装を直す。テストの期待値を変えるのは仕様が変わったときだけで、その変更は commit message に書く ／ 例: `fix: 仕様変更に伴い 400 期待を 422 に更新` ／ 失効: なし

## レビュー fan-out

回数は機械強制しない。収束したかどうかはメインエージェントが判断する。
並列起動と「要判断」で止まる規範は `core.md`（T0）にある。ここには実装レビュー固有の運用だけを置く。

- **観点は対象から選ぶ**: メインエージェントは、変更対象の言語・領域に合う reviewer を選ぶ ／ 例: DB migration を含むなら `database-reviewer` を足す ／ 失効: なし
- **指摘を 1 表に集約する**: メインエージェントは、全 reviewer の指摘を重複排除して 1 つの表 (重大度 / 指摘 / 対応) にまとめる ／ 例: 同じ指摘が 2 人から出たら 1 行にする ／ 失効: なし
- **重大度で対応を決める**: メインエージェントは、CRITICAL と HIGH を修正してから次に進み、MEDIUM 以下は対応か見送りかを表に記録する ／ 例: 「MEDIUM: 命名 → 見送り (別 task)」 ／ 失効: なし
- **修正後は再レビューする**: メインエージェントは、CRITICAL / HIGH を修正したら同じ reviewer を再起動し、新規指摘が出なくなるまで繰り返す ／ 例: 2 巡目で新規 CRITICAL が出たら 3 巡目を回す ／ 失効: なし
- **収束を記録する**: メインエージェントは、レビュー終了時に「何巡した / 残った未対応指摘」を task か PR 本文に 2 行で残す ／ 例: 「3 巡で収束。未対応: MEDIUM 1 件 (別 task 化)」 ／ 失効: なし

## commit

- **1 commit = 1 機能または 1 修正**: 実装者は、各 commit をテストが通る状態で切る ／ 例: 実装とそのテストを 1 commit にまとめる ／ 失効: なし
- **戻せる粒度を保つ**: 実装者は、`git revert <sha>` 1 回で機能単位を取り消せるように分割する ／ 例: リファクタと機能追加を別 commit にする ／ 失効: なし
- **Conventional Commits で書く**: 実装者は、`<type>: <要約>` 形式で commit message を書く ／ 例: `feat: ログイン失敗回数の上限を追加` ／ 失効: なし
- **commit 前に build・test・lint を通す**: 実装者は、3 つが green であることを確認してから commit する ／ 例: `npm run build && npm test && npm run lint` ／ 失効: CI が push 前に必ず落とす構成にしたとき
