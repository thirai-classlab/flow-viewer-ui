# 承認テンプレート（5 項目）

**承認を求めるすべての場面で使う型。** ルール追加に限らない — タスクの着手・完了・優先順の変更、設計 draft の承認、採用案からの逸脱、費用に影響する設定変更、元に戻せない操作、仕様やスコープの変更、いずれも同じ型で提案する。

`rules/core.md` の「**承認は判断材料つきで求める**」の本体がここ。T0 には 5 項目の名前だけを置き、**書き方と記入例はここ（T2）に置く**（常時ロードされない領域なので、量を気にせず書ける）。

---

## なぜ 5 項目なのか

**「〜してよいですか」だけでは、承認する側が判断できない。** 承認を求められた人が知りたいのは、少なくとも次の 5 つである。どれか 1 つでも欠けると、返事は「たぶん大丈夫」か「よく分からないので却下」のどちらかに寄る。

| 項目 | 承認する側が知りたいこと |
|---|---|
| **何をしたいか** | 具体的に何が変わるのか。**文面・コマンド・対象ファイルの全文** |
| **なぜ** | 今このタイミングで求められている理由。**このセッションで実際に起きた事実** |
| **しないとどうなる** | 断ったときの結果。**確かめていないなら「〜の可能性がある」** |
| **トレードオフ** | 得るもの / 失うもの / 副作用 |
| **どうやるか** | 手順・置き場・**数字（予算・件数・所要）**・いつから効くか |

## 型

**この 5 つの見出しを、この語のまま出す。** 語を言い換えると、読む側が「どれが欠けているか」を数えられなくなる。

```
### 提案: <一言で何を>

**何をしたいか**: 何が変わるか。**書く行・実行するコマンド・対象ファイルの全文**を出す
**なぜ**: きっかけになった事実。このセッションで実際に何が起きたか（日付・回数・観測した出力）
**しないとどうなる**: 断った場合に起きること。**推測なら「〜の可能性がある」と書く**（断定しない）
**トレードオフ**: 得るもの / 失うもの / 副作用
**どうやるか**: 手順と置き場、**現在値 → 変更後の値を数字で**、いつから効くか、戻し方
```

そのうえで `AskUserQuestion` を出す。**5 項目は本文に書き、選択肢の説明文に詰め込まない**（読みにくいうえ、切り詰められて肝心の数字が消える）。

| 選択肢 | 意味 |
|---|---|
| 承認する | そのまま実行する |
| 承認しない | 実行しない。**提案そのものを取り下げる**（言い換えて聞き直さない） |
| 修正して提案し直す | 指摘を受けて 5 項目を作り直し、もう一度出す |

## 各項目の書き方

### 何をしたいか

- **文面案そのものを見せる。** 「ルールを 1 件追加します」「タスクを 1 件始めます」では判断できない。追加する行、実行するコマンド、変える値を**そのまま**出す。
- 対象はフルパスで。「rules に足します」ではなく `.claude/rules/code.md`。
- ルール追加なら `_meta.md` の記述テンプレート（`- **<短い名前>**: <肯定形 1 行> ／ 例: <1 つ> ／ 失効: <いつ消せるか>`）で書いた**完成形**を。

### なぜ

- **このセッションで観測した事実だけ。** 「一般にありがちなので」は理由にならない。
- 事故なら**何回目か**を書く（`_meta.md` 条 1「二度目で書く」の判定に要る）。1 回目ならルール化せず記録で終える。
- タスクなら、なぜ**今**そのタスクなのか（依存が解けた / 期限 / 他の作業が止まっている）。

### しないとどうなる

- 起きることが**確かめられている**なら、根拠（過去の記録 / 失った時間）を添えて断定してよい。
- 確かめていないなら「〜の可能性がある」「〜は未確認」と書く。**推測を事実の語で書かない。**
- 「特に何も起きない」が正直な答えなら、そう書く。そのときはたいてい、やらないほうがよい。

### トレードオフ

- **得るもの**: どの作業が、どう変わるか。
- **失うもの**: 常時読まれる量、時間、費用、判断が 1 つ増えること、例外が出たときの摩擦。
- **副作用**: 既存のものとの重なり、範囲が広すぎないか（`settings.json` の正規表現が無害な操作まで止めないか等）。

### どうやるか

- 手順と置き場を具体的に。ルールなら**層**（T0 / T1 / T2 / `settings.json`）、T1 なら `paths:` の glob も。
- **数字を出す。** 予算なら `T0 4,231 → 4,300 tokens（警告 6,000 / 上限 10,000）`。タスクなら残り step 数。**目分量で「余裕があります」と書かない。**
- **いつから効くか**と**戻し方**。T0 は次のセッションから、T1 は次に該当ファイルを読んだ時から。

## 記入例 1: ルール追加

```
### 提案: bash の `grep -c` の戻り値を T1 に足す

**何をしたいか**: `.claude/rules/code.md` に次の 1 行を追記します。
  - **`grep -c` の戻り値**: メインエージェントは、`grep -c` の結果を `tr -cd '0-9'` に通してから
    数値比較する ／ 例: `n="$(grep -c x f | tr -cd '0-9')"` ／ 失効: なし
**なぜ**: 今回のセッションで `grep -c` が 0 件のとき `0` を出しつつ exit 1 を返し、`set -e` の下で
  スクリプトが落ちました。同じ事象は 2026-08-20 にも起きており、事故記録では 2 回目です。
**しないとどうなる**: 同じ書き方が再び入る可能性があります（前回は復旧に 30 分かかりました）。
  3 回目が必ず起きるとは言えません。ここは推測です。
**トレードオフ**: 得る = bash を書くときの判断材料が 1 つ増える。
  失う = `code.md` を読むセッションで 70 tokens 増える（bash を書かないセッションには影響しません）。
  副作用 = 既存の「シェルの落とし穴」の記述と重なりますが、あちらは背景で、これは規範です。
**どうやるか**: T1（`.claude/rules/code.md`、`paths: src/**, tests/**`）。
  予算は `code.md` 1,240 → 1,310 tokens（上限 2,000）。T0 は 4,231 のまま変わりません。
  次に `src/` か `tests/` を読んだ時から効きます。戻すときは該当行を消すだけです。
```

## 記入例 2: タスクの着手

```
### 提案: task-7（レート制限）に、依存を 1 件残したまま着手する

**何をしたいか**: `docs/tasks/list.md` の task-7 を `未着手` → `進行中` にし、branch
  `feat/rate-limit` を切って step 1（ミドルウェアの雛形）から始めます。
**なぜ**: task-7 の依存先は task-4（設定の外出し）と task-5（メトリクス）で、task-4 は完了
  済みですが task-5 が `進行中` です。今回確認したところ、step 1〜3 は task-5 の成果物を
  参照しません（参照するのは step 4 の計測部分だけ）。
**しないとどうなる**: task-5 の完了まで着手待ちになります。task-5 の残り step は 3 件で、
  完了時期はこちらでは見積もれていません（未確認）。
**トレードオフ**: 得る = step 1〜3 を先に進められる。
  失う = step 4 で task-5 の実装に合わせた手戻りが出る可能性があります。
  副作用 = branch が 2 本並走するので、`docs/tasks/list.md` の衝突に注意が要ります。
**どうやるか**: list.md の 1 行を書き換え、`git switch -c feat/rate-limit`。step 4 に入る前に
  task-5 の状態を再確認します。残り step は 5 件中 4 件。戻すときは status を `未着手` に
  戻して branch を消すだけで、成果物は残ります。
```

## 記入例 3: 費用や動きに影響する設定変更

```
### 提案: ultracode（深く考えて自動で手分けする）を有効にする

**何をしたいか**: `.claude/settings.json` に `"ultracode": true` を足します（戻すときは
  `ultracode` と `workflowSizeGuideline` の 2 つを外します）。
**なぜ**: このセッションで、複数ファイルにまたがる調査を 3 回手作業で分けました。
**しないとどうなる**: 手分けを毎回こちらで指示することになります。品質が下がるとは限りません。
**トレードオフ**: 得る = 手分けが自動になる。
  失う = **利用量（費用）が増えます**（増加量はこちらでは測れていません。未確認です）。
**どうやるか**: `.claude/settings.json`。常時読まれる量は変わりません（4,231 のまま）。
  書き換え後に `python3 -m json.tool` を通し、失敗したら元へ戻します。次のセッションから
  効きます。戻し方は上記の 2 キーを外すだけです。
```

## 悪い例 → 良い例

| 悪い例 | なぜ悪いか | 良い例 |
|---|---|---|
| 「ルールを 1 件追加してよいですか?」 | 何が書かれるか分からない | 追加する行を**全文**出す |
| 「予算に余裕があります」 | 数字が無く、確かめようがない | 「T0 4,231 → 4,300 tokens（警告 6,000）」 |
| 「放置すると事故が再発します」 | 推測を事実の語で書いている | 「再発する**可能性があります**。前回は 30 分失いました。3 回目が必ず起きるとは言えません」 |
| 「デメリットは特にありません」 | トレードオフを考えていない | 「失う = 該当ファイルを読むセッションで 70 tokens 増える」 |
| 「タスクを始めます。よろしいですか?」 | どのタスクを、なぜ今か、が無い | 「task-7 を、依存先 task-5 を残したまま step 1〜3 だけ先行させます。理由は…」 |
| 5 項目を `AskUserQuestion` の選択肢の説明文に詰め込む | 切り詰められて数字が消える | 5 項目は**本文**、選択肢は 3 つの短いラベルだけ |
| 断られたあと、言い換えてもう一度聞く | 承認しない = 取り下げ、の約束が壊れる | 取り下げて記録に残す。再提案は新しい事実が出てから |

## 使う場面

`commands/` を全部 grep して洗い出した、承認を求める箇所（v1.14.0 時点）。**この表に無い場面でも、user の承認を求めるなら同じ型を使う。**

| 場面 | コマンド | どこ |
|---|---|---|
| ルール追加 | `add-rule.md` | 工程 ⑥ の配置前 / 工程 ⑤ の削除候補 |
| ルールの提案（セッション終わり） | `state.md` | 手順 11 |
| ルールの棚卸し（降格・失効の判断） | `rules-audit.md` | 分類 3・4 を user に選ばせるところ |
| 設計 draft の承認 | `new-draft.md` | 手順 5 |
| タスク着手（依存が未完了のとき） | `start-task.md` | 手順 3 |
| タスク完了（step が残っているとき）/ `main` への push・PR 取り込み | `finish-task.md` | 手順 4 / 末尾 |
| commit の分割 / 元に戻せない操作 | `commit.md` | 手順 3 / 「承認が要る操作」 |
| 費用や動きに影響する設定変更 | `config.md` | 2（ultracode）/ 7（更新の自動化） |
| 参照されていないファイルの削除 | `verify.md` | 6 |

**この型を使わない場面**（判断材料の要らないところで 5 項目を出すと、本当に要る場面での重みが落ちる）:

- 承認が要らないもの — T2 と `docs/` への追記、ルールの**削除**（`_meta.md` 条 8）、`rules-audit.md` の分類 1・2。
- 元に戻す方向の変更 — 設定を無効に戻す、費用が減る方向。
- **user が自分から指示したこと** — 「有効にして」「これを消して」と言われた操作に、改めて 5 項目を出さない。
- 選択肢の提示であって承認ではないもの — `/init` の初期設定 3 問のような「どれにしますか」。
